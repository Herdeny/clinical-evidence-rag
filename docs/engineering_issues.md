**ENG-001：回答有引用，但补出了证据中没有的具体指南名**

**现象与证据。** DEV-01 的生成输入只有 `F_SCOPE`、`AC_INCIDENTAL`、`AC_RADIOGRAPH` 三张卡。回答在“证据支持的判断”中加入了“如 Lung-RADS 一类筛查专用体系”，但输入证据没有提供这个名称。初版回答及输入记录见 [B1 初版实验快照](../results/b1_dev01_top3_initial.json)，源代码见 [B1 Notebook](../b1_practice.ipynb) 的提示词单元。

**分析。** 需要分开检查：引用的 ID 是否来自输入、引用内容是否支持相邻判断、适用条件是否匹配。合法的 ID 和链接本身不能证明整句话受到支持。当前现象能证明新增名称缺少本轮证据支持，不能据此确定模型内部如何产生了这个名称，也不等同于判定该名称在医学上错误。

**处理计划。** 进一步要求模型分开表述“有证据支持的判断”与“待核验的候选检索线索”。具体指南名和医学建议也要核对支持关系。后续可设计结论到证据的结构化映射和核验步骤，目前尚未实现自动审计。

**验收。** 同一报告、同一 Top-3、同一模型设置下重新生成。材料中未获支持的名称不能作为已证实结论；如保留为补查线索，应明确标记待核验。再在其他开发题上复测，避免只针对 DEV-01 调整。

**2026-11-12 复查。** [新保存的回答](../results/b1_dev01_top3_followup_01.json) 在判断部分更明确地承认材料没有给出筛查框架的具体名称，但补查段仍出现 Lung-RADS，候选线索的标记尚需明确。保存的源码已增加四条规则，但实际请求消息尚未与该响应绑定核验，因此不能把文字变化直接归因为这些规则生效，相关疑点见 ENG-009。

**用户最新提交后的更新。** 用户随后提供了输入 674、输出 922、总计 1596 tokens、结束原因为 stop 的本次回答。回答不再把当前材料没有提供的具体指南名称写成已证实结论，并单列“待核验的候选线索”。本题这一项表现改善，后续还需要在其他题上检查。对应 [用户最新提交记录](../results/b1_dev01_top3_user_reported_02.json) 保存了统计和经过排版整理的摘录，不冒充完整原始 API 响应。

**同题证据量对照。** 在 [Top-3／全量实验](../results/b1_dev01_top3_vs_all.json) 中，全量组能使用 `LR_SCOPE` 给出具体框架名称，Top-3 组的主要结论则承认缺少该项依据。这支持关键证据缺口影响了本题回答的观察。仍需逐条核验其他判断；全量组也没有完整列出原文链接等来源字段，不能将这一处改善当作全部引用要求已满足。

**ENG-002：缺失信息与追问偏离当前问题**

**现象与证据。** DEV-01 问的是选择哪份指南，以及什么事实决定这一选择。初版回答扩展到了结节分类和随访间隔，并集中列出尺寸、既往影像等条件。这些内容需要说明与本题的关系，不能一概当作回答当前问题之前必须补齐的信息。证据见同一份 [B1 初版实验快照](../results/b1_dev01_top3_initial.json)。

**分析。** “报告没有写某个字段”和“当前任务必须知道这个字段”是两个不同判断。模型虽然使用了“报告缺少条件”和“检索材料不足”两个标题，但任务范围还不够明确，仍然可能泛化出一张缺项清单。

**处理计划。** 让模型先明确本题要回答的任务，再说明每个缺项会阻碍哪个判断。当前问题的必要条件与后续更细任务才需要的条件分开表述；证据缺口应指向补查资料，病例事实缺口才指向追问。

**验收。** 已提供的信息不重复追问；每项追问或补查建议都说明与当前问题的关系。源码已加入任务边界规则，仍待确认改动实际进入请求并完成复测。

**2026-11-12 复查。** 新保存的回答仍提出先补齐大小和形态等条件，并给出“任何结节管理框架分层的核心参数”“部分筛查框架的分类依赖此信息”等本轮卡片没有支持的概括。这里记录的是证据支持关系和任务范围问题，不对这些概括的医学真实性作独立判断。问题继续保持未解决状态。

**用户最新提交后的更新。** 674／922 tokens 的回答仍将大小、形态、吸烟史等作为下一步需要补齐的条件，讨论重心扩展到具体分类、随访和资格核对。本题问的是框架选择；这些补充条件与当前问题的必要关系仍未说明，相关医学概括也未获得本轮三张卡的支持。ENG-002 继续保留为失败项，不能因 ENG-001 改善就将其一并标为解决。

**同题证据量对照。** Top-3 和全量组都继续展开分类、随访、风险背景等问题。全量组还逐条讨论了多张本题不需要的卡片，输入证据更多没有自动解决任务范围扩展。当前保持失败项，后续在扩充数据集上继续检查。

**当前能据实回答。** 单题生成暴露了过度列缺项的问题。计划把缺失条件绑定到当前决策任务，同时区分病例信息缺失与检索证据不足；目前还没有完成自动追问策略或 Agent 路由。

**ENG-003：项目转述在提示词中被称为原文**

**现象与证据。** 证据卡和上下文明确标记“证据正文（项目转述）”，但初版 `human` 消息仍使用“证据原文”的称呼。`system` 与 `human` 对资料性质的描述不一致。

**分析与处理计划。** 来源链接、文件定位、项目转述和逐字摘录需要保持区别。统一提示词中的资料称呼，原文尚未核验时不把转述包装成直接引文。后续若增加原文摘录，应另外保存摘录文本和定位信息。

**验收。** 模型输入的资料标签一致，回答能正确表明所用内容的性质。2026-11-12 复查时，system 已强调转述，但 human 中两处“证据原文”仍未修改，当前不满足措辞统一要求。

**后续源码检查。** 在开始全量证据对照前，已确认 human 中两处称呼都改成了“证据卡（项目转述）”。资料标签的源码修正已完成，后续仍检查模型是否把转述写成直接原文引文。

**面试可能问。** “证据卡带有官网链接，就算原文引用吗？”

**当前能据实回答。** 链接和定位用于回查，但项目转述仍然是转述。当前卡片不代表已经完成逐字引文核验。

**已做处理。** 将报告和问题构造成固定格式的字符串，整体传入检索函数。B0 结果文件现在保存了 `retrieval_query`，可以回查实际使用的报告和问题。见 [逐题结果](../results/b0_dev_results.jsonl) 和 [B0 Notebook](../b0_practice.ipynb)。

**验证范围。** 已检查 DEV-01 的完整输入。修正输入链路后，目标卡仍排第 6，因此输入修复与检索效果需要分别验收。

**ENG-005：主题相关性高，但目标证据排序靠后**

**现象与证据。** 在完整报告加问题的输入下，DEV-01 的 `LR_SCOPE` 排第 6，显示得分为 `0.692640`；前三为 `F_SCOPE`、`AC_INCIDENTAL`、`AC_RADIOGRAPH`。按现有标注，本题 Recall@3 和 Recall@5 均为 0。完整排名保存在 [B0 Notebook](../b0_practice.ipynb) 的单题诊断输出中。

**分析。** 目标证据存在于库中，问题表现为未进入前 K 的排序漏检。报告背景词可能影响整体向量，但目前没有消融实验，不能把“语义稀释”写成已证实原因。相似度分数也不是正确概率或适用性证明。

**后续计划。** 保留失败样例，在相同数据版本上比较 BM25＋RRF、重排和查询改写。全量证据输入用于生成阶段的对照；扩大 K 的诊断结果不能代替原定 K 的基线结果。

**新增观察。** 同题证据量对照中，补齐 `LR_SCOPE` 等卡后，模型能给出受到材料支持的具体框架名称。这里只能支持本例关键证据缺口影响生成的解释，不能据一个病例认定其他错误也都由检索造成，或证明全量上下文在所有任务上更好。

**当前能据实回答。** 排名可能让目标卡落在上下文之外。已分别保存检索失败和下游生成表现，后续需要检查改善发生在召回、排序还是生成环节。

**ENG-008：召回率聚合口径错误**

**现象与证据。** 初版把三个 K 的逐题召回率列表拼在一起求平均，得到一个总数，丢失了不同 K 的表现。DEV-03 有两张标注卡，检出其中一张时应为 0.5，不能只记录“至少命中一张”。

**已做处理。** 每题按前 K 项与标注 ID 集合的交集计算召回率，分母为标注卡总数；然后对每个 K 分别做逐题平均。实现和八道题的检索结果已独立复算，见 [B0 摘要](../results/b0_dev_summary.json)。

**验证范围。** Recall@1、@3、@5 分别为 0.5625、0.6875、0.6875。检查了范围和逐题单调性，示例及 DEV-01 也符合预期。当前所有题的标注列表非空，尚未定义空标注任务的指标口径。

**面试可能问。** “Recall@3 达到 68.75% 具体是什么意思？”

**当前能据实回答。** 在这八道合成开发题上，先按各题标注证据计算 Recall@3，再取平均。它不是有至少一次命中的题目比例，也不是医学回答准确率。

**ENG-009：Notebook 旧变量和旧输出掩盖当前代码状态**

**现象与证据。** 重构评测循环时，留下了依赖旧 `eval_df`、`new_eval` 的拼接语句；也多次出现当前源码已修改，但保存的输出仍是上一次的报错。另有结果列表复用了原始题表的 `cases` 变量名。

**已做处理。** 清理旧拼接语句，使用 `eval_rows` 保存评测记录，最后统一建表。审阅时同时核对源码、错误栈和输出，不把旧报错直接归因到当前代码。

**验证边界。** 已清理可见的遗留变量依赖并得到八题结果，但尚未保存独立的干净内核全流程验收记录。不能据此声称已完成跨环境部署验证。

**2026-11-12 当时提出的疑点（已撤回作为本轮排障依据）。** 对照初版快照，当时保存的源码中 system 文本从 303 个字符增加到 428 个字符，文本哈希也已变化，但新旧保存输出的输入 token 数都为 593。该份输出为 803 个输出 token、总计 1396，结束原因为 stop。助手因此建议额外核对实际消息，但没有先确认这些文件输出是否代表用户最新运行。历史材料见 [当时的复查快照](../results/b1_dev01_top3_followup_01.json)，后续修正如下。

**评审失误修正。** 用户随后提交了 674 输入、922 输出、总计 1596 tokens 的最新回答。先前助手没有先确认文件输出是否对应这次运行，就将相同 token 数作为主要排查依据并要求额外检查，造成了不必要的排障。这属于助手评审流程失误，不是用户没有执行代码的证据。对本次执行的疑虑已撤回，当前评审以用户提交的最新结果为准。

**证据使用规则。** 对话中明确提交的当次输出、文件中保存的历史输出和当前可编辑源码需要标明各自来源与时点。它们可能属于不同运行，发现不一致时先核对记录对应关系。token 数只是运行统计，不能单独证明某条提示词规则已生效或未生效；也不应为了追查助手的错误判断反复要求用户调用 API。

**处理计划。** 后续完善运行日志时，在调用前冻结实际消息，将同一次调用的消息、模型配置与响应一起保存。源码中的模板和当前内存中的 PromptValue 可能属于不同执行状态，仅重建可编辑源码不足以证明某次历史请求内容。这项日志改进独立于本轮内容评审，不再作为接受用户最新输出或继续实验的前置条件。

**面试可能问。** “为什么 Notebook 里能运行，换环境后却报变量未定义？”

**面试可继续追问。** “怎么确认一次提示词改动确实发给了模型？”需要检查实际消息并建立请求与响应的对应记录，再判断输出变化，不能只根据编辑器中看到的新源码作结论。这个问题当前已定位到需要补充日志，尚未完成对应关系验收。

**ENG-013：增加证据后出现适用范围串用和触发条件转述偏移**

**ENG-019：检索算法在小库跑通，不等于大库的运行成本已验证**

**已做处理与后续。** 固定数据、参数、库版本和同分规则，保留原样 CLI、输入／代码／结果指纹与执行源文件副本；指标独立复算通过。下一步完成同一语料的 CUDA Dense 编码和缓存，再比较及融合。任何后端或数据变化须另记配置并测量，不把原 v2 小库 CUDA Dense 与本轮大库 CPU BM25 的差别直接归因于算法。没有宣称已实现 GPU BM25 或生产级延迟优化。

**面试可能问。** “为什么 BM25 没放 GPU，扩库后是否仍能满足运行要求？”

**ENG-020：单个模型加载参数未必约束整个依赖链的网络访问**

**实际现象。** 2026-11-19，使用当前LangChain HuggingFaceEmbeddings／Sentence Transformers加载已缓存的BGE固定revision，model_kwargs包含local_files_only=True。首次真实CUDA小批仍观察到对huggingface.co上main/processor_config.json的HEAD探测和SSL重试；随后八条正文与查询编码成功。只能据实说明观察到了辅助配置探测，不能据此断言权重被更新或来自main。

**处理与验证。** 保留原模型及固定revision，在进程启动前额外设置HF_HUB_OFFLINE=1、TRANSFORMERS_OFFLINE=1。同样八条样本复核成功，实际内部batch_size=8，GPU为RTX 4090、模型设备cuda:0，输出(8,384)、float32、L2范数约1，复用时正文编码调用为零。首次与离线复核结果分别保存于results/dense_cuda_preflight_initial.json和results/dense_cuda_preflight.json；正式审计记录这两个非敏感开关。两次单次加载耗时受缓存与设备预热等因素影响，不据此宣称加速比例。

**运行环境区别。** 默认工具隔离环境没有/dev/nvidia0，nvidia-smi与torch.cuda失败；获准的GPU执行环境中显卡和模型编码正常。先区分设备可见性与驱动故障，再确定措施，本轮没有修驱动或改成CPU编码。

**面试可能问。** “设置了local_files_only，为什么仍有网络日志？如何保证离线复现？”

**当前能据实回答。** 实测发现加载链会探测辅助配置，因此除了固定revision和缓存身份，还在整个进程启动前启用Hub与Transformers离线模式，保留实际配置、源码指纹与验证结果。不能只凭一个参数就声称整个依赖链完全离线。
